# MCM Personal Editorial Engine — 개발 구현 계획 (2026-08-11)

기술 스택: Next.js 16.3.0 / React 19.2.8 / Tailwind CSS 4 / TypeScript 5

---

## 1. MVP 스코프 (2인팀 · 3~4주 기준)

**데모에서 실제로 구현할 것 (AI당위성을 증명하는 핵심)**
- 신호3 — AI Meaning Match(이 연결이 고객에게 새로운 의미 있는 발견인가?) — 실제 Claude API 호출로 판단 + reason·headline·caption 생성. AI가 실제로 일하는 유일한 지점이라 반드시 실동작
- 취향 프로필 계산(축3개 가중 집계) — 단순 로직으로 구현
- "MY MCM" 웹 피드 UI — Issue 카드 목록 + 확장뷰

**데모에서는 시뮬레이션 버튼으로 대체할 것**
- 신호1·2 실시간 감지 → "새 도시 구매 발생", "2개월 경과" 같은 시나리오를 버튼 클릭으로 수동 트리거
- Phase1→Phase2 자동전환 → 데모 계정에 Issue 개수를 미리 세팅해서 즉시 시연
- 카카오톡/이메일 실제 발송 → 목업 화면만 (실제 알림톡 API 연동 없음)

**이번 데모 스코프 밖 (로드맵으로만 명시)**
- 정반대매칭형 A/B/C 자동 로테이션 전체 이력 관리 → 데모에선 A타입 예시 1개만 시연
- 헤리티지 소재 라이브러리 전체 → 2~3개 예시만 미리 작성

**도시별 Global 소비 데이터 출처**
- 실제 서비스: MCM 내부 POS/재고 데이터 API 연동(매장별 판매 데이터) 전제
- 데모: 서울/도쿄/파리/베를린 4개 도시 × 각 5~10개 제품(컬러·실루엣·모노그램밀도 태그 포함)으로 직접 큐레이션한 더미 데이터 사용. "추후 실제 POS 데이터로 교체 가능"이라는 standalone 설계 전제를 명시

## 2. 데이터 저장 방식

**전체 데이터 Supabase로 통일**

```
Supabase
├── customers
├── products
├── city_signals
└── issues
```

- 정적 데이터(cities/products)와 초기 customers도 Supabase 테이블로 통일 — 코드에서 접근 방식이 하나로 일관되고, 초기 데이터는 seed 데이터로 넣는다
- 서버리스 배포 환경(Vercel 등)에서는 파일시스템 쓰기가 불안정해서, 계속 쌓이는 issues 이력이 로직 대부분(기준2 중복체크·Phase1→2 전환·다양성 체크)의 기반이 되는 만큼 처음부터 실제 DB로 통일하는 게 안전. 팀 자체 선례 있음(Rabot 재고 인텔리전스 후보, Supabase 단일테이블로 실현가능성 18/20 최고점 기록)

**Supabase 테이블 스키마**
- `customers`: id, name, purchase_history(jsonb: {product_id, purchased_at, city}[]), interest_history(jsonb: {product_id, interested_at, type}[]), taste_profile(jsonb: {color, silhouette, monogram_density, confidence}), created_at
- `products`: id, name, city, color, silhouette, monogram_density, image_url, category(참고용), popularity_score(참고용, 필터링에 안 씀)
- `city_signals`: id, city, description(서술형 요약), related_product_ids(jsonb), detected_at, processed(bool) — 신호1 이벤트 로그
- `issues`: id, customer_id(FK), issue_number, type(discovery/contrast/heritage), city, axis_used(다양성 체크용), headline, caption, source_signal, published_at

**데이터 모델 참고사항**
- `products.city`는 "이 제품이 어느 도시에서 발견되는가"를 표현하기 위한 데모용 단순화. 실제로는 한 제품이 여러 도시에서 판매될 수 있어 정규화상 이상적이진 않지만, 데모 스코프에서는 허용

## 3. API 설계

**라우트 목록**
- `POST /api/simulate/purchase` — 도시 구매 시뮬레이션(신호2)
- `POST /api/simulate/city-trend` — 도시 트렌드 시뮬레이션(신호1)
- `POST /api/simulate/time-skip` — 2개월 경과 시뮬레이션(하한선)
- `POST /api/issues/generate` — 후보생성→기준1·2 필터→기준3(Claude)→통과시 issues 저장
- `GET /api/issues?customer_id=X` — MY MCM 피드 조회
- `GET /api/customers/:id/taste-profile` — 취향 프로필 조회/재계산

**`/api/issues/generate` 실행 순서**
```
simulate(신호1 or 신호2 트리거)
 ↓
candidate 조회 (city_signals / products)
 ↓
취향 프로필 계산
 ↓
기준1 (취향축 겹침)
 ↓
기준2 (이전 Issue와 중복 아님)
 ↓
후보가 남으면
 ↓
Claude 기준3 호출
 ↓
passes=true → headline/caption 받아 issues 테이블에 저장
passes=false → Issue 생성하지 않고 종료
```

**기준3 프롬프트 구조**
- 입력: Global 후보(도시·제품·속성·서술신호) + 고객 취향 프로필(3축) + 최근 Issue 2~3개(헤드라인+사용된 축)
- 출력(구조화 JSON): `{ passes: boolean, reason: string, headline: string, caption: string }`
- passes=false → Issue 생성하지 않음 / passes=true → headline·caption으로 Issue 생성
- **언어: 전체 영어, 럭셔리 매거진 에디토리얼 톤** — 타깃이 글로벌 고객(90%+ 해외매출)이라 한국 고객은 영어 이해 가능성 높고 해외 고객은 한국어 이해 어려움 → 로케일 분기 없이 영어로 통일. 컬러/실루엣 등 취향 속성은 스펙시트가 아니라 문장 속에 자연스럽게 녹여서 서술 (예: "The mini silhouette you love, reimagined in deep navy for Tokyo.")

**에러 처리**
- Claude API 호출 실패 → Issue 생성하지 않음 + 오류 반환
- Supabase 호출 실패 → 사용자에게 오류 표시
- Claude 응답 JSON 파싱 실패 → 재시도 또는 fallback 처리

**취향 프로필 계산 (의사코드)**
```
items = 구매이력(가중치2) + 관심이력(가중치1)
각 item에 최신성 감쇠 적용(오래될수록 가중치 ↓)
축(컬러/실루엣/모노그램밀도)별 가중집계 → 최빈값 채택
전체 가중치 합 < 최소기준 → confidence='unconfirmed'(Stage0)
```

## 4. 프론트엔드 구조

### 4.1 화면 구성

```
① MY MCM (피드)
 ├─ 현재 고객의 Editorial 아카이브
 ├─ Issue 01 / 02 / 03 ... 누적, 최신 Issue 강조
 ├─ Issue마다 도시·테마·대표 이미지 노출
 └─ 스크롤로 잡지 아카이브처럼 탐색 (카드 탭 → Issue Detail 이동)

② Issue Detail (카드 형식 아님, 세로 스크롤 한 페이지 — 여러 섹션으로 구성)
```

### 4.2 Issue Detail 섹션 구조

```
[ HERO ]
TOKYO / ISSUE 03 / 큰 Editorial 이미지
 ↓
[ STORY ]
AI가 만든 Editorial — 제목 + 본문 (기준3 headline/caption)
 ↓
[ WHY YOU ]
왜 이 이야기가 당신에게 연결됐는지, 문장으로 자연스럽게 설명
 ↓
[ DISCOVERY ]
TOKYO — 이번에 발견된 MCM, 관련 제품 이미지(에디토리얼 이미지로, 카탈로그 나열 아님)
 ↓
[ EXPERIENCE ]
MCM TOKYO — 매장/도시 정보 (구매 링크 아닌 라벨, 정확한 카피는 미정)
 ↓
[ END ]
Your next MCM story — 다음 호에 대한 여운/기대감
```

**확정된 원칙**
- 구매 유도 CTA 버튼 없음 (전과정/구매 CTA는 스코프 밖 — 문제정의에서 의도적으로 뺀 영역과 일치)
- 카드 탭을 통한 이동(피드 → 상세)은 있음, 단 "구매하기" 류 버튼은 없음
- 취향 속성(컬러·실루엣·모노그램밀도)은 스펙시트로 나열하지 않고 STORY/WHY YOU 문장 속에 자연스럽게 녹여서 서술
- 카피는 전체 영어, 럭셔리 매거진 에디토리얼 톤
- 한 Issue 안 여러 섹션이 하나의 이야기를 순서대로 풀어내는 구조 — "한 번에 하나만 보여줌"(진열대처럼 안 보이게) 원칙과 배치되지 않음. 여러 상품/이슈를 동시 나열하는 게 아니라 하나의 서사를 깊이 있게 전개하는 것


## 5. 개발 순서 (백엔드/API와 프론트 병행, 시간 부족 시 뒤부터 트리밍)

1. 데이터 + 취향프로필 + 기준1·2
2. 기준3 / Claude API 연동
3. 프론트 기본 뼈대 + 핵심 화면 (백엔드 완료 기다리지 않고 병행 시작, mock 데이터로 우선 구현 후 API 연동)
4. Phase1/2 우선순위 로직
5. Stage0 헤리티지 대체
6. 상한선(월1회 체크)
7. 하한선 + 정반대매칭형(A/B/C, 시간 부족 시 A타입만)
8. 통합 테스트 / UI 다듬기 / 배포
