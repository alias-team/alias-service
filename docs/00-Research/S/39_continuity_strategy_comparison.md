# Step 4. S1-B + S3-C 결합 가능성

## 4.1 Core Loop — 하나의 반복 Loop로 설명 가능한가

### 후보 Loop

```
① 여정 이해        고객의 다음 목적지·기간·성격
       ↓
② 관계 판단        이 제품이 그 여정의 어느 장면에 놓이는가   ← Core AI
       ↓
③ 선택            고객이 제품과 자기 여정의 관계를 확인하고 결정
       ↓
④ 실제 여행        판단이 현실에서 검증되거나 어긋난다
       ↓
⑤ 여정이 바뀐다    다음 목적지·기간·성격이 달라진다
       ↓
       └──────→ ① 로 복귀. 같은 판단, 다른 답
```

### 🟢 성립한다 — 세 가지 근거

| # | 근거 |
| --- | --- |
| **1** | **②에서 일어나는 판단이 매 회차 동일하다.** 새로운 판단이 추가되지 않는다 |
| **2** | **회차마다 답이 달라지는 이유가 서비스 안에 있다** — 여정이 바뀌기 때문이다. 신제품 출시나 캠페인 같은 **서비스 밖 이유가 필요 없다.** `18` P-02의 판별 질문("두 번째로 쓸 이유가 서비스 안에 있는가?")에 답할 수 있다 |
| **3** | **⑤가 자동으로 발생한다.** MCM 고객은 **글로벌 디지털 노마드**이고 매출의 90%+가 이동 고객에서 나온다 [QA-4-1, A급 공식]. **여정이 바뀌는 것은 이 고객군의 정의 그 자체다** |

### ⚠️ Loop가 무너지는 조건

| 조건 | 왜 무너지는가 |
| --- | --- |
| **⑤의 트리거가 `시간`이면** | "구매 30일 후"는 여정과 무관하다. **CRM 자동화가 되고 `36`의 S3-B(46점 최하위)로 회귀한다** |
| **④에서 브랜드가 개입하면** | 여행 중 알림·후속 연락은 마케팅 푸시가 된다. **④는 브랜드가 아무것도 하지 않는 구간이어야 한다** |
| **①이 매 회차 개인 프로필을 두껍게 만들면** | GATE-1 위반 방향으로 누적된다 |

> ## 🔒 판별선
> **다음 접점의 트리거는 `시간 경과`가 아니라 `새 여정의 발생`이어야 한다.**
> 시간 트리거 = CRM = 탈락. 여정 트리거 = 같은 Core AI = 성립.

## 4.2 Core AI — 결합 이후에도 하나로 설명 가능한가

### 압축 시도

> **AI가 고객과 제품의 관계를 `지금의 여정` 기준으로 다시 해석한다.**

**이 한 문장이 Loop의 모든 회차를 덮는가?**

| 회차 | AI가 하는 일 | 같은 판단인가 |
| --- | --- | --- |
| 1회차 (첫 공항) | 방콕 5일 × 제품 3개 → 장면 배치 | — |
| 2회차 (다음 공항) | 헬싱키 3일 × 제품 3개 → 장면 배치 | 🟢 **동일** |
| 3회차 (그다음) | 리야드 10일 × 제품 3개 → 장면 배치 | 🟢 **동일** |

**입력만 바뀌고 판단 함수는 동일하다.** 출력 형식도 동일하다(장면).

### 🔴 결합 거부 조건 대조 — 사용자 제시 기준

> "만약 **구매 전 AI / 구매 후 AI / CRM AI**처럼 서로 다른 AI 기능 세 개가 필요하면 결합을 거부한다."

| AI | 필요한가 | 판정 |
| --- | --- | --- |
| **구매 전 AI** | 여정 × 제품 → 장면 | 🟢 필요 |
| **구매 후 AI** | ❌ 불필요. 여행 중 브랜드는 아무것도 하지 않는다 (§4.1 ④) | 🟢 **없음** |
| **CRM AI** | ❌ 불필요. 재방문 예측·타이밍 판단을 하지 않는다 | 🟢 **없음** |

> ## 🟢 **AI는 하나다. 결합을 거부할 이유가 없다.**

### 4.3 그렇다면 S3-C에서 실제로 가져오는 것은 무엇인가

**⚠️ S3-C를 통째로 붙이는 것이 아니다.** `36`에서 S3-C의 약점은 ① AI Necessity 8/12(C1의 반복 적용에 가깝다) ② Standalone 2/3(세션 연결 미해결) ③ Conversion 5/9였다.

| S3-C의 구성 요소 | 가져오는가 | 이유 |
| --- | --- | --- |
| **여정 간 판단의 이어짐** | 🟢 **가져온다** | Core Loop ⑤가 이것이다 |
| **"이번엔 아닙니다"의 재평가** | 🟢 **가져온다** | 같은 Core AI의 출력 |
| 개인 세션 연결 인프라 | 🟡 **개념만** — Step 5에서 방식 선택 | 미해결 리스크 |
| 축적된 고객 이해·프로필 | 🔴 **버린다** | 개인 프로필 = GATE-1 위험 + CRM 회귀 |
| 지난 구매 이력 기반 제안 | 🔴 **버린다** | X-01 회귀 |

**즉 결합이 아니라 `S1-B의 Core AI가 두 번 이상 돌 수 있게 하는 것`이다**(Inference·높음). **Feature 합치기가 아니라 같은 판단의 반복 실행이다.**

## 4.4 Complexity 증가량 점검

사용자 규칙: *"Complexity가 늘어나면 오히려 감점한다."*

| 축 | S1-B 단독 | 결합 후 | 증가 |
| --- | --- | --- | --- |
| AI 판단 수 | 1 | **1** | **0** |
| 화면 수 | 1 (여정 → 장면) | 2 (여정 → 장면 / 이어받기) | +1 |
| 데이터 저장 | 없음 | 판단 결과 1건 | +1 |
| 고객이 배워야 할 것 | 0 | **0** (Step 5의 방식에 따라) | **0** |
| 설명 문장 수 | 1 | **1** | **0** |

**판정: Complexity 증가가 작다**(Inference·중간). 다만 **`고객이 배워야 할 것 0`은 Step 5의 보존 방식 선택에 달려 있다** — 방식이 잘못되면 이 값이 올라가고 그 순간 결합은 감점 요인이 된다.

## 5.2 🟢 가장 유망한 방식 — ④ Digital Pass 개념

**이유는 기술이 아니라 무대에 있다.**

| # | 근거 | 등급 |
| --- | --- | --- |
| **1** | **공항에서 고객은 이미 Wallet에 탑승권을 넣고 다닌다.** 새 행동을 학습시키지 않는다 | 무대의 정의상 (Inference·높음) |
| **2** | `18` **G-07(Human-centered AI)** 판별 질문 — "고객이 이것을 쓰기 위해 무언가를 배워야 하는가?" **답이 `아니오`인 유일한 방식** | [QA-3-3, A급 공식] |
| **3** | `18` **G-08(Natural Experience)** — "이 개입이 흐름 안에 있는가?" **탑승권 옆에 Pass가 하나 더 놓이는 것은 흐름 안이다** | [QA-3-3, A급 공식] |
| **4** | **Pass에는 개인 식별자가 없어도 된다.** 담기는 것은 `이 여정에서 이 제품이 어디 놓였는가`이지 `누구인가`가 아니다 | GATE-1 정합 (Inference) |
| **5** | **고객이 물리적으로 소유한다.** 브랜드 서버에 프로필이 쌓이지 않으므로 "감시받는다" 인식을 구조적으로 차단한다 | G-06·G-09 정합 (Inference) |

### ⚠️ ④의 한계

| # | 한계 |
| --- | --- |
| **1** | **실제 Apple Wallet / Google Wallet 연동은 2명·3주 범위를 벗어날 가능성이 높다**(Hypothesis) |
| **2** | 고객이 Pass를 **저장하지 않으면 Loop가 끊긴다** — 저장 의향은 미검증 |
| **3** | **iOS·Android 이원화**가 MVP 부담을 키운다 |

## 5.3 MVP 조합 제안

**단일 방식이 아니라 계층으로 둔다**(Inference).

```
[개념 설계]   ④ Digital Pass — 확장 시 실제로 갈 방향. 피칭에서 이것을 말한다
                    ↓
[MVP 구현]    ③ QR / Pass 형태 + ① Local Device — 3주 안에 실제로 도는 것
                    ↓
[Demo 시연]   ⑧ Synthetic Continuity — 두 여정의 시간 간격을 압축해 3분 안에 보인다
```

**⑦ 브라우저 local storage는 단독 채택하지 않는다.** 다른 기기·다른 브라우저에서 끊기는데, **다음 공항에서 이어지는 것이 이 Loop의 전부**이므로 치명적이다.

**⑥ 일회성 anonymous key도 채택하지 않는다.** 의미 없는 문자열을 고객이 보관해야 하며 G-07(학습 부담)·G-08(흐름 이탈)을 동시에 위반한다.

## 5.4 `12` API-Readiness 대응 (`21` E-13 요건)

> **"독립개체 standalone로 설계한 후 이후 특정 데이터가 API로 물린다는 것을 전제로 기획"** [QA-5-3, A급 공식]

| 항목 | 내용 |
| --- | --- |
| **연결 대상** | ① 실제 운항 정보(취항지·게이트·시간) ② MCM 제품 카탈로그 ③ Wallet Pass 발급 API |
| **연결 시 변화** | 목적지 더미 → 실제 노선. 제품 더미 → 실제 SKU·재고. QR → 네이티브 Pass |
| **개인정보 경계** | **세 연결 모두 개인 식별자를 요구하지 않는다.** 운항 정보는 공개, 카탈로그는 공개, Pass는 익명 발급 가능 |
| **승인 주체** | 운항 정보는 공항·항공사 / 카탈로그는 MCM / Pass는 플랫폼 |

**🟢 이 설계의 강점: API가 물려도 개인정보 경계가 바뀌지 않는다**(Inference·높음). `36`에서 S3-B가 탈락한 이유(확장 시 개인 이력 필요)가 여기서는 발생하지 않는다.

| **⚠️ 무너지는 조건** | **다음 접점의 트리거가 `시간`이 되는 순간** CRM 자동화로 회귀한다. 트리거는 반드시 **`새 여정의 발생`**이어야 한다 |

## 이 문서의 한계

1. **§4.1 Loop의 ⑤(여정이 바뀐다)가 자동 발생한다는 것은 `Inference`다.** MCM 고객의 실제 여행 빈도 데이터가 없다.
2. **§5.2의 "고객이 Pass를 저장할 것"은 `Hypothesis`다.** 저장 의향에 대한 직접 근거가 0이다 — **이것이 결합 전략의 최대 미검증 지점이다.**
3. **Wallet 연동의 3주 구현 가능성을 검증하지 않았다**(Hypothesis). 기술 검토 없이 개념 수준으로만 판단했다.
4. **§4.4의 Complexity 증가량은 정성 추정**이며 실측이 아니다.
5. **`36`이 S3-C에 준 71점은 S3-C 전체에 대한 것**이고, 이 문서는 그중 일부만 가져왔다. **가져온 부분만의 점수를 별도로 계산하지 않았다** — `40`에서 전략 단위로 재평가한다.
6. **기술 구현을 상세 설계하지 않았다.** 사용자 지시에 따른다.
