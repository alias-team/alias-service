# 1. TEST 1 — Taste Discovery Kill Test

## 1.1 🔴 결정적 문제 — **제시된 예시 데이터가 주장을 무너뜨린다**

사용자가 제시한 입력:

```
Product A: brown, large, low monogram, soft leather, slouchy form, ▶low saturation◀, minimal hardware
Product B: burgundy, medium, low monogram, suede, curved form, ▶low saturation◀, minimal hardware
Product C: olive, large, no monogram, soft leather, relaxed form, ▶low saturation◀, organic shape
```

기대 출력: **"이 고객은 Brown을 좋아하는 것이 아니라 채도가 낮은 색조에 반복적으로 반응한다."**

> ## 🔴 **`low saturation`이 이미 입력 태그에 있다.**
>
> **이 "발견"은 `saturation` 속성의 빈도 집계다. 새로운 축의 발견이 아니다.**

**두 번째 예시도 같다.** *"Low Monogram + Soft Leather + Minimal Hardware → understated expression"* 은 **세 태그의 공기(co-occurrence)**이며, **Association Rule Mining(Apriori·FP-Growth)이 정확히 이것을 하는 알고리즘**이다.

## 1.2 Non-LLM 대체 수단별 검증

| 방법 | 대체 가능한 것 | 대체 못 하는 것 |
| --- | --- | --- |
| **속성 빈도 집계** | `low saturation` 반복 발견 | 조합 |
| **🔴 Association Rule Mining** | **`low_monogram + soft_leather + minimal_hardware` 규칙 발견 — support·confidence·lift까지 함께 산출** | 이름 붙이기 |
| **Embedding + 평균** | 상호작용 제품 벡터의 중심 = taste vector. **실무 표준이며 매우 강력** | 설명 |
| **Clustering** | 고객 상호작용을 군집화 → 군집 중심이 미적 패턴 | 명명 |
| **Feature engineering** | 파생 속성 생성 (예: 채도 = f(color)) | — |

**LLM이 실제로 추가하는 것:**

| 기여 | 성격 |
| --- | --- |
| `pattern` 이름 ("Muted tonal palette") | **명명 — 표현층** |
| `reason` 문장 | **서술 — 표현층** |
| 태그에 없는 상위 개념 생성 | 🔴 **§1.3에서 차단됨** |

## 1.3 🔴 그리고 evidence 요구가 LLM을 태그 안에 가둔다

**사용자가 명시한 제한:**
> *"반드시 실제 행동 데이터와 제품 속성을 evidence로 가져야 한다."*
> `evidence_product_ids: ["A", "B", "C"]`

**이 제한은 G-04(근거 없는 생성 설명) 방어로는 옳다.** 그러나 **동시에 LLM이 태그 공간 밖으로 나가는 것을 구조적으로 금지한다**(Inference·높음).

```
태그 밖으로 나가면  →  evidence 없음  →  규칙 위반
태그 안에 머물면    →  association rule로 대체 가능
```

> ## 🔑 **`52` · `55`에서 두 번 기록한 패러독스의 세 번째 반복이다 — 안전하게 만들수록 룰이 된다.**

## 1.4 판정

> ## **Non-AI 잔존: ~80%**

**`55`의 85%에서 5%p 개선.** 사유는 축이 고정 3개가 아니라 **태그 공간 전체의 조합**으로 넓어져 단순 최빈값으로는 부족해지고 **Association Rule이 필요해졌다**는 점이다. 그러나 **여전히 전통 데이터마이닝의 영역이며 LLM 필연성이 아니다.**

# 2. TEST 2 — 새로운 축인가, 재명명인가

> ## 🔴 **재명명이다.**

| 증거 | 내용 |
| --- | --- |
| **1** | **`low saturation`이 입력 태그에 이미 존재한다** (§1.1) |
| **2** | **`evidence_product_ids` 요구가 태그 밖 개념을 금지한다** (§1.3) |
| **3** | **출력 `pattern`은 결국 태그 조합의 라벨**이다 — "Material-led expression" = `low_monogram + soft_leather + minimal_hardware` |

## 🟡 다만 `55`보다는 낫다

| | `55` | `56` |
| --- | --- | --- |
| 탐색 공간 | **고정 3축** | **태그 공간 전체의 조합** |
| 필요한 Non-AI 기법 | 가중 최빈값 | **Association Rule Mining** |
| 조합 수 | 3 | 태그 N개 → 2^N 부분집합 |

**조합 폭발이 생긴 것은 사실이다.** 그러나 **조합 폭발은 AI 필연성의 필요조건이지 충분조건이 아니다** — Apriori는 정확히 조합 폭발을 다루기 위해 만들어진 알고리즘이다.

## 🔒 진짜 새 축이 되려면

| # | 조건 |
| --- | --- |
| **1** | **태그에 없는 차원을 읽어야 한다** → Vision (TEST 3) |
| **2** | **태그 간 비선형·조건부 관계를 발견해야 한다** — 예: *"이 고객은 가방에서는 절제를, 지갑에서는 과감함을 택한다"* (카테고리 조건부 취향). **현재 설계에 이 개념이 없다** |

**2번이 흥미롭다.** Association Rule은 조건부 규칙을 찾을 수 있으나, **"왜 그 조건에서 다른가"를 설명하지 못한다.** 여기에는 LLM 여지가 있다(Hypothesis).

# 3. TEST 3 — Product Data Requirement

## 3.1 🔴 "축을 사전 정의하지 않는다"는 주장이 성립하지 않는다

**사용자가 제시한 예시 데이터의 축을 세어 본다:**

```
color · size · monogram density · material · form · saturation · hardware  =  7개
```

> ## 🔴 **3축에서 7축으로 늘어났을 뿐, 사전 정의는 그대로다.**
>
> **누군가 `saturation`이라는 축을 미리 정의하고 모든 제품에 값을 매겨야 이 시스템이 작동한다.**

**그리고 이것은 사람의 노동이다** — MCM 제품 수백 개 × 7축 × 값 부여. **데모에서는 가능하나(4개 도시 × 5~10개 제품), 실서비스에서는 큰 부담이다**(Inference).

## 3.2 🟢 Vision Model은 실제로 이 문제를 완화한다

| | 태그 기반 | Vision 기반 |
| --- | --- | --- |
| 축 정의 | 🔴 **사람이 사전 정의** | 🟢 **불필요 — 임베딩 공간이 축을 대신한다** |
| 새 차원 발견 | 🔴 불가 | 🟢 **가능** |
| **설명** | 🟢 가능 (태그 이름) | 🔴 **불가 — 임베딩은 말을 못 한다** |

## 3.3 🔑 그리고 여기서 LLM의 진짜 자리가 나온다

```
Vision Embedding  →  클러스터를 찾는다        (설명 불가)
        +
LLM               →  그 클러스터를 언어화한다  (근거: 클러스터 대표 이미지들)
        =
▶ 태그에 없던 축을 발견하고 이름을 붙인다 ◀
```

> ## 🟢 **이것이 이 구조에서 LLM이 전통 ML로 대체되지 않는 유일한 조합이다**(Inference·중간~높음).

**⚠️ 그러나 세 가지 문제가 있다.**

| # | 문제 |
| --- | --- |
| **1** | **3주 MVP 부담** — 제품 이미지 수집 + 임베딩 + 클러스터링 + LLM 언어화 파이프라인 |
| **2** | **검증 불가** — LLM이 붙인 이름이 맞는지 확인할 방법이 없다 |
| **3** | **G-04 위험 재발** — 이미지에서 "읽어 낸" 설명은 evidence가 이미지뿐이다 |

| **C. 충분히 누적 (5건+)** | 🟢 가능 | **발행** |

## 🔴 그러나 사업적 위험이 남는다

| 근거 | 내용 | 등급 |

**🔒 데모에서 반드시 보여야 할 것:** 최소 조건 미달 고객에게 **아무것도 발행되지 않는 화면.** 그것이 이 설계의 정직성이자 차별점이다.

# 5. TEST 5 — Editorial Worthiness

## 5.1 🟢 score threshold와 구조적으로 다르다

| | Score Threshold | **Editorial Worthiness** |
| --- | --- | --- |
| 절차 | 입력 → 점수 → 임계값 비교 | 입력 → **서술 시도** → 성공/실패 |
| 판정 시점 | **계산으로 사전 결정** | **시도해 봐야 안다** |
| 계산 성격 | O(1) 비교 | **생성 후 평가** |
| 실패의 의미 | 점수 미달 | **말할 것이 없음** |

> ## 🟢 **`55`에서 `선택 문제`로 후퇴했던 것이 정확히 복원됐다.**
>
> **`54`의 신호3 기준3(`구체적이고 뻔하지 않은 한 문장으로 설명 가능한가`)이 돌아왔고, 사용자가 여기에 4개 판정 기준을 추가해 더 명확해졌다.**

## 5.2 🔴 그러나 심각한 실무 위험 하나

> **LLM이 자기 출력을 평가하면 대체로 "통과"라고 답한다.**

| 위험 | 내용 |
| --- | --- |
| **자기 평가 편향** | 방금 자기가 쓴 Editorial Angle에 대해 "이게 뻔한가?"를 물으면 LLM은 관대하다 |
| **결과** | 🔴 **거의 항상 발행된다 → `발행하지 않음`이 허구가 된다 → 차별점 소멸** |

### 🔒 완화 (택일)

| # | 방법 |
| --- | --- |
| **A** | **생성과 판정을 분리한다** — 별도 호출에서, 자기가 썼다는 사실을 모른 채 평가 |
| **B** | **판정을 상대 비교로** — "지난 3개 Issue와 비교해 이것이 새로운가" (절대 판단보다 안정적) |
| **C** | **거부 사례를 프롬프트에 넣는다** — few-shot으로 "이런 건 뻔하다" 예시 제공 |

**🔴 이 완화가 없으면 TEST 5의 개선이 실전에서 무효화된다.** 데모에서 **미발행 사례가 실제로 나오는지**가 검증 지표다.

## 5.3 판정

## 6.2 전체 잔존율

| 버전 | 잔존 | AI 지점 | 게이트의 성격 |
| --- | --- | --- | --- |
| `54` | **45%** | **1개** | 서술 가능성 |

## 6.3 🔑 왜 `54`(45%)보다 여전히 나쁜가

> ## **AI 필연성은 합이 아니라 평균에 가깝다.**

```
54:  강한 AI 1개                 → 평균이 높다
55:  약한 AI 4개                 → 평균이 무너진다
56:  강한 AI 1개 + 약한 AI 1개   → 평균이 희석된다
```

**AI #2(35~40%)는 `54`의 신호3과 같은 수준이거나 더 강하다. 그런데 AI #1(80%)이 붙어서 전체 평균을 끌어올렸다**(Inference·높음).

**🔴 심사 반박이 이 구조를 정확히 찌른다:** *"Taste Discovery는 association rule로 되는데 왜 LLM을 쓰나요?"*

# 7. MVP 실현 가능성

| 항목 | `54` | `55` | **`56`** |
| --- | --- | --- | --- |
| LLM 호출 지점 | 1 | 4 | **2** |
| 프롬프트 세트 | 1 | 4 | **2** |
| 체이닝 | 없음 | 3단 | **1단** |
| 추가 필요 기술 | — | — | 🟡 **Association Rule 또는 Vision** |

**🟡 2인·3주에 가능은 하다.** 다만 **Vision 파이프라인을 넣으면 불가능에 가깝다**(Inference).

## 🔒 최소 구현안 — 권고

```
1. 고객 행동 데이터 (구매 + 관심)                     [더미]
2. 제품 속성 태그 (7축)                               [더미, 사람이 큐레이션]
3. ▶ Association Rule로 패턴 추출 ◀                   [RULE — LLM 아님]
4. 후보 Retrieval (도시 신호 × 패턴)                  [RULE]
5. ▶ AI: Editorial Angle 서술 시도 + 자기 아닌 평가 ◀  [LLM 1~2회]
6. Issue 저장 또는 미발행                             [RULE]
```

## 🔴 권고: **AI #1을 LLM에서 룰로 되돌린다**

| 근거 |
| --- |
| **AI #1 잔존 80% / AI #2 잔존 35~40%** — **자원을 강한 곳에 몰아야 한다** |
| Association Rule은 라이브러리(mlxtend 등)로 즉시 구현되며 **support·confidence·lift가 근거로 함께 나온다** — evidence 요구를 오히려 더 잘 충족한다 |
| **패턴 이름은 태그 조합을 그대로 쓰면 된다.** 예쁜 이름이 필요하면 AI #2의 Editorial 문장 안에서 자연스럽게 나온다 |

**이렇게 하면 LLM 1회, `54` 구조로 복귀하되 취향 추출이 3축 → 조합 규칙으로 개선된다.**
