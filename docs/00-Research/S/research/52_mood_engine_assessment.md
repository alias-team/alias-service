# 1. CRM 추천 문제 — 🟢 Main은 풀고 🔴 Sub가 되돌린다

## 1.1 🟢 순서를 뒤집은 것은 실질적 개선이다

```
[CRM]           신제품 출시 → 누구에게 보낼까 → 배정
                 ▲ 모든 신제품이 반드시 누군가에게 배정된다 (재고 소진 논리)

[Main Engine]   고객 Mood 생성 → 그 Mood와 만나는 시즌 제품이 있는가
                 ▲ ▶ 없을 수도 있다 ◀
```

**🔑 이 구조는 "이번 시즌엔 당신의 방향과 만나는 게 없습니다"를 가능하게 한다.** `46`·`51`에서 계속 찾던 **"아무것도 제안하지 않는 출력"**이 여기서 자연스럽게 나온다(Inference·높음).

**⚠️ 그러나 설계에 명시돼 있지 않다.** Step 4는 "해당 Mood와 연결되는 제품/스타일 선택"이라고만 되어 있어 **항상 찾는 것을 전제**한다. 명시하지 않으면 구현에서 "무조건 3개 매칭"이 된다.

## 1.2 🔴 Sub Engine이 차별성을 상쇄한다

> **Sub Engine: "Stark Backpack + Wishlist Silver Charm → New Season Charm Collection 연결"**

**이것은 정확히 두 가지다:**

| | 대응 서비스 |
| --- | --- |
| 제품 간 호환성 연결 | 🔴 **Stylitics Complete the Look** — AOV +39%, 주요 프로그램의 90%+ 구동 [Fact] |
| 위시리스트 제품을 지면에 노출 | 🔴 **Abandoned Cart 리타게팅** — `51` §1에서 지적한 W-1 위반 |

**"보조 정보로 활용"이라는 위치 지정은 방어가 되지 않는다**(Inference·높음).

| # | 이유 |
| --- | --- |
| **1** | **Mood는 추상적이고 제품 연결은 구체적이다.** 고객은 구체적인 것을 본다 |
| **2** | **심사위원도 그것을 본다.** "Main은 해석이고 Sub는 보조입니다"는 말이지, 화면에는 제품이 있다 |
| **3** | **Sub가 있으면 Main의 "없을 수도 있다"가 무력화된다** — Main이 못 찾아도 Sub가 찾아 준다 |

> ## 🔴 **Sub Engine은 Main Engine이 만든 유일한 차별점을 지운다.**

# 2. Mood 생성이 충분한 개인화인가 — 🔴 조건부

## 2.1 결정적 질문 — **Mood는 몇 개인가?**

| Mood 설계 | 성격 | 판정 |
| --- | --- | --- |
| **사전 정의 목록** (Personalized Traveler · Urban Luxury · …) 8~12개 | **페르소나 세그먼트** | 🔴 **개인화가 아니다** |
| **AI가 생성** | 개인화 | 🔴 **다른 위험** — §2.2 |

**심사 반박:** *"그럼 고객을 8개 유형으로 나누는 건가요?"*

**유형 분류는 마케팅에서 가장 오래된 도구다.** `42` D-1에서 이미 경계했다 — **"유형은 남과 비교하게 만들고, 서명은 자기 것이다."**

## 2.2 🔴 그렇다고 생성하면 다른 위험이 온다

**`44`에서 확인한 실측 사례가 정확히 여기 적용된다.**

> **Spotify Wrapped 2024는 최다 장르·최다 앨범을 빼고 `창작된 마이크로 장르` 목록을 제공했다가 조롱의 대상이 됐다.** AI 생성 콘텐츠는 **"공허한 관찰(empty observations)"**, 인사이트가 **일반적(generic)**이라는 반응을 얻었다. [**Fact**]

**AI가 만든 정체성 라벨은 공허하게 느껴질 위험이 크다**(Inference·높음). 그리고 `18` G-04(근거 없는 생성 설명 금지)에도 걸린다.

## 2.3 🔴 그리고 해석 엔진 고유의 위험 — 틀렸을 때의 비용

| | 추천 엔진 | **해석 엔진** |
| --- | --- | --- |
| 출력 | 제품 | **의미** |
| 틀렸을 때 고객 반응 | 안 산다 | **"브랜드가 나를 이렇게 본다고?"** |
| 비용 | 낮다 | **높다 — 관계 훼손** |

**`18` G-01의 판별 질문 — "이 출력이 틀렸을 때 고객은 누구를 탓하는가?" — 의 답이 `브랜드`다.**

> ## 🔑 **Mood 라벨링은 상품 추천보다 G-01 위험이 크다.**

**이것이 이번 검증에서 나온 새 지적이다.** 지금까지 해석 엔진을 추천 엔진보다 안전하다고 암묵적으로 가정해 왔는데, **틀렸을 때의 비용은 반대다.**

# 3. Main / Sub 구조 — 🔴 부적절하다

## 3.1 MCM 요구와 정면 충돌

> **"아이디어 단순 나열보다 아이디어를 보다 뾰족하게 풀고자 하는 문제/솔루션에 `투영`하여 피칭하시는 게 중요합니다."** [QA-1-2, **A급 공식**]

**`21` E-10(Single Core Capability, 5점)의 판정 기준:** *"하나의 판단·생성·해석·연결로 압축되는가? 나머지를 제거해도 가설 검증이 성립하는가?"*

**엔진이 둘이면 이 질문에 `아니오`다.** E-10이 4 → 3으로 내려간다.

## 3.2 🟢 대안 — Sub를 없애거나 Main 안으로

| 선택 | 결과 |
| --- | --- |
| **① Sub Engine 제거** | 🟢 **가장 깨끗하다.** 차별점이 복원되고 E-10이 회복된다. 대가: 제품 연결 정보가 사라져 전환 근거 약화 |
| **② Sub를 Main의 출력 형식으로 흡수** | 🟡 Mood가 정해지면 **그 Mood에 속하는 제품이 자동으로 따라온다.** 별도 엔진이 아니라 렌더링 |
| ③ 현재대로 유지 | 🔴 E-10 감점 + 차별성 상쇄 |

**②가 현실적이다** — 제품이 나오되 **Mood 판단의 귀결로** 나오고, **위시리스트 제품은 여전히 제외**한다.

# 4. AI vs 룰 구분 — 🔴 여기가 가장 심각하다

## 4.1 단계별 판정

| # | 단계 | 실제로 하는 일 | AI인가 |
| --- | --- | --- | --- |
| 1 | 제품 태그 추출 (Travel·Black·Monogram) | 카탈로그 메타데이터 조회 | 🔴 **룰** |
| 2 | Customer MCM DNA 추출 (반복 요소) | **빈도 집계** | 🔴 **룰** |
| 3 | Wishlist 방향 파악 (Silver Charm → Personalization) | 태그 조회 | 🔴 **룰** |
| 4 | **Mood Expansion** | DNA + 방향 → Mood | 🟡 **목록이면 룰 / 생성이면 AI (§2.2 위험)** |
| 5 | Season Matching | 태그 매칭 | 🔴 **룰** |
| 6 | Sub Engine 호환성 | 제품 관계 그래프 | 🔴 **룰 (Stylitics가 하는 것)** |

> ## 🔴 **6단계 중 5개가 룰이다. Kill Test 잔존 ~75%.**

## 4.2 🔑 이번 수정의 패러독스

> ## **구조를 명확하게 만들수록 AI가 사라졌다.**

| | `51` | `52` |
| --- | --- | --- |
| 구조 명확도 | 🟡 모호 | 🟢 **명확** |
| AI 필연성 | 6/12 | 🔻 **5/12** |

**이유(Inference·높음):** 각 단계를 명확히 정의하는 것은 **곧 그 단계를 룰로 쓸 수 있게 만드는 일**이다. "AI가 Mood를 판단한다"가 모호할 때는 판단처럼 보였는데, `DNA 추출 → 방향 파악 → Mood 매핑`으로 쪼개니 **집계·조회·매핑**이 됐다.

**이것은 설계가 나빠서가 아니라 정직해져서 생긴 결과다.** 그리고 정직해진 결과 **AI가 필요 없다는 것이 드러났다.**

## 4.3 🟢 그럼 AI는 어디에 있어야 하는가

**`51` §3.3에서 찾은 것이 여전히 유일하게 유효하다.**

| # | 자리 | 왜 AI인가 | 강도 |
| --- | --- | --- | --- |
| **A** | 🟢 **Mood와 만나는 시즌 제품이 없을 때** | ① 대비로 연결할지 ② 한 다리 건너 연결할지 ③ **이번 호를 안 낼지.** 룰로 답이 없는 유일한 지점 | 🟢 **가장 강함** |
| **B** | 🟢 **이미 열었던 Mood를 피할 때** | `49` §6 미루기. 이력이 축을 만든다 | 🟢 강함 |
| C | 태그가 사전 정의되지 않을 때 | 제품 이미지·설명에서 추출 | 🟡 중간 |

**→ Main Engine의 Step 1~3은 룰로 두고, AI는 Step 4의 `매칭 실패 처리`에 두어야 한다**(Inference·높음).

# 6. MCM 차별성을 넣는 법 — 🟢 이번 구조에 자리가 생겼다

## 6.1 지금 왜 없는가

> Expanded Mood: **Personalized Traveler** / **Urban Luxury**

**Mood 축이 범용이다.** Urban / Minimal / Street / Formal — 어느 브랜드나 쓴다. **Prada로 로고를 바꿔도 성립한다.**

## 6.2 🟢 Mood의 `축` 자체를 MCM 언어로 바꾼다

**이번 구조에서 MCM 자산이 들어갈 자리는 `Mood를 무엇으로 나누는가`다**(Inference).

| | 일반 Mood 축 | **MCM Mood 축** |
| --- | --- | --- |
| 기준 | 스타일 (Urban / Minimal / Street) | **이동의 성격** |
| 예 | "Urban Luxury" | **"매달 다른 도시로 가는 사람" / "한 도시에 오래 머무는 사람" / "짐이 늘 같은 사람"** |
| 근거 | — | **매출 90%+가 이동 고객** [QA-4-1, **A급 공식**] · **"글로벌 디지털 노마드이며 Gen MZ"** [QA-4-1] |

### 왜 이것이 유일하게 작동하는가

| # | 이유 |
| --- | --- |
| **1** | 🟢 **로고 치환에 무너진다** — Prada 고객을 `이동의 성격`으로 나누는 것은 브랜드에 근거가 없다. **MCM만 매출 구조로 뒷받침한다** |
| **2** | 🟢 **`43`과 축을 공유한다** — `Made for Movement`가 두 방향의 공통 언어가 된다 |
| **3** | 🟢 **charm에 기능적 근거가 생긴다** — 장식이 아니라 **수많은 검은 가방 중 내 것을 알아보게 하는 표식** [`51` §5.2] |
| **4** | 🟡 **Mood 라벨의 G-01 위험이 줄어든다** — "당신은 Urban Luxury입니다"는 성격 규정이라 반발할 수 있지만, **"당신은 자주 이동합니다"는 관측이라 반발하기 어렵다** |

**⚠️ 4번이 §2.3 위험의 완화책이기도 하다.** 스타일 라벨은 정체성 규정이고, 이동 패턴은 사실 서술이다.

**⚠️ 다만 전부 `Hypothesis`다.** 그리고 **이동 데이터를 어디서 얻는가**가 미해결이다 — 구매 이력만으로는 이동 빈도를 알 수 없다. **`43`이 면세를 무대로 삼은 이유가 여기 있다.**

# 7. 상품 추천 엔진 vs 브랜드 경험 해석 엔진

| 축 | 추천 엔진 | 해석 엔진 |
| --- | --- | --- |
| 입력 → 출력 | 고객 → **제품** | 고객 → **의미** |
| 성공 지표 | 🟢 **명확** (클릭·전환) | 🔴 **없다** |
| 검증 | 🟢 A/B 테스트 | 🔴 **불가** |
| 틀렸을 때 비용 | 🟢 **낮다** (안 산다) | 🔴 **높다** (관계 훼손) |
| 아무것도 안 내는 출력 | 🔴 없다 | 🟢 **가능** |
| 브랜드 자산 필요성 | 🟡 카탈로그면 충분 | 🟢 **세계관이 있어야 성립** |

## 🔑 이 표에서 나오는 두 가지

**① 해석 엔진의 우위는 `아무것도 안 낼 수 있다`와 `브랜드 세계관이 필요하다` 두 칸뿐이다.**
→ **그런데 현재 설계는 두 칸을 다 못 쓰고 있다.** Sub Engine이 첫 칸을 지우고(§1.2), Mood 축이 범용이라 둘째 칸도 비었다(§6.1).

**② 해석 엔진은 검증할 수 없고 틀렸을 때 비싸다.**
→ 이것을 감수할 이유가 있어야 한다. **현재는 그 이유가 "더 브랜드답다" 수준이며 근거가 아니다.**

> ## 🔒 한 줄 판별
> **추천 엔진은 `무엇을 살까`에 답하고, 해석 엔진은 `내가 지금 어떤 사람인가`에 답한다.**
> **후자는 틀리면 더 아프다. 그러니 라벨은 성격이 아니라 관측이어야 한다.**
