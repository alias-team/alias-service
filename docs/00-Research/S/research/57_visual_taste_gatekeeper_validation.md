# B. Visual Taste Discovery

## B.1 🟢 타당성 — 직전 문제를 실제로 해결한다

**`56` §1·§3에서 지적한 것:** *예시 데이터에 `low saturation`이 이미 태그로 있었고, 7개 축을 사람이 사전 정의했으므로 "축을 없앴다"는 주장이 성립하지 않는다.*

**이미지 입력은 이 지적을 정면으로 해소한다.**

| | 태그 기반 (`56`) | **이미지 기반 (`57`)** |
| --- | --- | --- |
| 축 정의 | 🔴 사람이 7개 사전 정의 | 🟢 **없음** |
| 태그 밖 차원 | 🔴 **구조적으로 불가** | 🟢 **가능** — 소재의 광택, 하드웨어와 몸체의 비율, 형태의 긴장도 등 |
| 태깅 노동 | 🔴 제품 수백 × 7축 | 🟢 **0** |

**→ 이것은 말장난이 아니라 입력 구조의 실제 변경이다**(Inference·높음).

## B.2 🔴 그러나 세 가지 문제가 남는다

| # | 문제 | 심각도 |
| --- | --- | --- |
| **1** | **모델이 자기 사전(prior)을 갖는다.** 축이 *우리*에게 정의되지 않았을 뿐, **VLM의 학습 데이터가 정의한 표현 공간 안에 있다.** 그리고 그것은 **검사도 통제도 불가능하다** | 🟡 중간 — 사람 7축보다는 넓으나 무한하지 않다 |
| **2** | 🔴 **검증 불가능성이 커졌다.** 태그 기반이면 `saturation=low`를 대조할 수 있었다. 이미지 기반이면 **AI가 "Muted tonal expression"이라고 했을 때 맞는지 확인할 방법이 눈으로 보는 것뿐**이다. `18` G-01(틀렸을 때 브랜드 귀책)이 커진다 | 🔴 **높음** |
| **3** | **출력이 결국 속성 어휘로 돌아온다.** 예시의 `reason`: *"Although the **hues** differ, ... restrained **tonal contrast**"* — hue·tonal contrast는 속성 이름이다 | 🟢 낮음 — 이것은 표현이지 발견 메커니즘이 아니다 |

## B.3 Non-AI 대체 — **이론과 1주 MVP를 분리한다**

### 이론적 대체 (~65% 잔존)

| 방법 | 대체 가능한 것 |
| --- | --- |
| **CLIP / DINOv2 임베딩** | 제품 이미지를 벡터로. **시각 유사도를 매우 잘 잡는다** |
| **클러스터링** | 고객 상호작용 제품의 군집 → 군집 중심 = 취향 벡터 |
| **차원 축소 + 축 해석** | 주성분이 "밝기", "복잡도" 같은 축에 대응하는 경우가 많다 |

🔴 **이론적으로는 상당 부분 대체된다.** "이미지니까 AI가 필요하다"는 논리는 성립하지 않는다.

### 🟢 그러나 대체되지 않는 것 두 개

| # | 내용 |
| --- | --- |
| **1** | **임베딩은 말을 못 한다.** 그런데 이 파이프라인에서 **Taste Pattern은 AI #2(Gatekeeper)의 입력**이다. **벡터를 넘길 수 없다.** 언어화가 필수이고, 클러스터를 언어화하려면 결국 VLM이 필요하다 |
| **2** | 🔴 **소표본에서 클러스터링이 성립하지 않는다.** 고객당 제품 **5~8개**로 클러스터링은 통계적으로 무의미하다. **VLM은 5개 이미지를 보고 바로 패턴을 말할 수 있다** |

### 1주 MVP 현실적 대체 (~35~40% 잔존)

| 필요 작업 | 태그/임베딩 방식 | VLM 방식 |
| --- | --- | --- |
| 이미지 수집 | 필요 | 필요 |
| 임베딩 파이프라인 구축 | 🔴 **필요** | 🟢 불필요 |
| 클러스터링 + 튜닝 | 🔴 **필요 (그런데 5~8개로는 무의미)** | 🟢 불필요 |
| 결과 언어화 | 🔴 **결국 LLM 필요** | 🟢 한 번에 |

> ## **B 답: 이론 ~65% / 1주 MVP ~35~40%**
>
> **해커톤 AI Necessity는 후자 기준으로 평가하는 것이 타당하다**(Inference).

# C. Purchase > Wishlist

## 🟢 타당하다

**구매는 비용을 지불한 선택이므로 implicit feedback 중 가장 강한 신호다.** 추천시스템 실무의 표준 위계와 일치한다(Inference·높음).

## 🔴 그러나 럭셔리에서는 반례가 있다

| 반례 | 내용 |
| --- | --- |
| **1** | **구매는 선물일 수 있다** — 본인 취향이 아니다 |
| **2** | 🔴 **구매는 가격 제약을 받는다.** 럭셔리에서 **위시리스트가 오히려 진짜 욕망**일 수 있다 — 구매한 것은 "지금 살 수 있는 것", 담아 둔 것은 "언젠가 갖고 싶은 것" |
| **3** | 구매는 시점이 오래됐을 수 있고 위시리스트가 최신이다 |

## 🔒 MVP에서 가장 설명하기 쉬운 방식 — **가중치가 아니라 역할 분리**

| | 역할 |
| --- | --- |
| **Purchase** | **취향의 기반** — "이 고객이 반복해 온 미감" |
| **Wishlist** | **확장 방향** — "지금 눈이 가 있는 곳" |

**가중치(2:1)는 숫자라 설명이 어렵고 반례에 취약하다. 역할 분리는 한 문장으로 설명되고 §2의 반례를 흡수한다**(Inference·중간~높음). `50`에서 이미 도달했던 구조다.

# D. Evidence Grounding

## 🔴 현재 구조는 Grounding이 아니라 **출처 표시**다

| 시스템이 검증하는 것 | 검증하지 않는 것 |
| --- | --- |
| ID가 입력에 존재하는가 | 🔴 **그 제품이 실제로 그 패턴을 보이는가** |
| Purchase인지 Wishlist인지 | 🔴 **패턴이 그 제품들을 실제로 설명하는가** |

**AI가 A·B·C를 "Muted tonal"의 근거로 댔는데 C가 형광 오렌지여도 시스템은 통과시킨다.**

## 🔒 1주 MVP에서 추가할 것 — 비용 순

| # | 방법 | 비용 | 효과 |
| --- | --- | --- | --- |
| **1** | 🟢 **Evidence 이미지를 화면에 나란히 노출** | **거의 0** | **검증을 사람(심사위원)에게 넘긴다.** "AI가 이 셋을 근거로 댔습니다" → 이미지 3장 → 보는 사람이 판단. **가장 싸고 가장 설득력 있다** |
| **2** | 🟢 **반대 증거 요구** — *"이 패턴에 맞지 않는 제품이 있는가?"*를 함께 묻는다 | 프롬프트 한 줄 | 있으면 confidence 하향. **AI가 자기 패턴의 반례를 스스로 찾게 하는 것이 확인 비용이 가장 낮은 검증이다** |
| **3** | **패턴당 최소 evidence 2개 + 지지 비율** | 룰 몇 줄 | 3개 중 3개 vs 8개 중 2개를 구분 |
| 4 | 별도 호출로 패턴↔제품 일치 검증 | LLM 1회 추가 | 1주에는 부담 |

**→ 1·2·3만 넣어도 Grounding이라 부를 수 있는 수준이 된다.**

# F. Editor / Gatekeeper 분리

## F.1 🟡 Self-approval 문제를 **완화하지만 해결하지 못한다**

| | 내용 |
| --- | --- |
| 🟢 **완화되는 이유** | 프롬프트가 다르면 초점이 다르다. 생성 맥락(무엇을 쓸까)과 평가 맥락(이게 가치 있나)이 분리된다 |
| 🔴 **해결되지 않는 이유** | **같은 모델은 같은 사전확률을 공유한다.** Editor가 "좋다"고 판단해 생성한 것을, 같은 모델이 같은 이유로 좋다고 볼 가능성이 높다. 그리고 **LLM은 열린 평가 질문에 관대하다**(Inference·중간~높음) |

**→ "같은 모델 2회 호출"만으로는 부족하다.**

## F.2 🔒 1주 MVP에서 가장 현실적인 방법 — 3개 조합

| # | 방법 | 비용 | 효과 |
| --- | --- | --- | --- |
| **1** | 🟢 **익명화 + `없음` 허용** — Gatekeeper에게 **3개 후보 Angle을 순서 섞어 익명으로** 주고, **"발행할 가치가 있는 것을 고르되, 없으면 없다고 답하라"** | 프롬프트 설계만 | **자기 것인지 모르게 하고, `전부 통과`를 구조적으로 어렵게 만든다** |
| **2** | 🟢 **절대 판단 → 상대 비교** — *"이 Angle이 지난 3개 Issue보다 새로운가"* | 입력 추가 | 절대 판단보다 안정적 |
| **3** | 🟢 **거부 사례 few-shot** — "이런 건 뻔하다" 예시 2~3개 | 프롬프트 | 판정 기준을 구체화 |

**⚠️ 순서를 뒤집는 방법(Gatekeeper 먼저 → Editor 나중)은 채택하지 말 것.** 그러면 **"써 봐야 안다"가 무너지고 threshold로 회귀**한다 [`56` I].

# I. 전체 AI Kill Test

| 제거 대상 | 무엇이 무너지는가 |
| --- | --- |
| Visual Taste Discovery | 🟡 **이론적으로는 임베딩+클러스터로 대체. 1주에는 불가** |

## 🔴 그런데 정직하게 — Gatekeeper도 일부는 대체된다

| Gatekeeper의 판정 | Non-AI |
| --- | --- |
| "너무 비슷함" 거절 | 🔴 **유사도 상한으로 구현 가능** |
| 지난 Issue 반복 | 🔴 축 거리로 구현 가능 |
| **"할 말이 있는가"** | 🟢 **대체 불가** — 유사도가 중간이어도 할 말이 없을 수 있다. **써 봐야 안다** |

**→ Gatekeeper의 세 판정 중 둘은 룰이고 하나만 AI다.** 그러나 **그 하나가 이 서비스의 정의다.**

# J. "추천 엔진 + LLM 카피"와 구별되는가

> ## 🟢 **구별된다. 단 한 지점 때문이다.**

```
추천 엔진 + LLM 카피:   후보 스코어링 → 상위 선택 → 카피 생성 → ▶항상 발행◀
이 구조:                후보 → ▶Angle을 써 본다◀ → ▶독립 판정◀ → PASS/REJECT
```

| 구별되는 지점 | 구별되지 않는 지점 |
| --- | --- |
| 🟢 **써 본 뒤에야 발행 여부를 안다** | 🔴 후보 Retrieval은 동일 |
